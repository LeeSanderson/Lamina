## Answers

1. **Reading `<LaminaLayer>`.** Ship a `build/Lamina.Analyzers.props` (file name must equal the package ID) holding `<CompilerVisibleProperty Include="LaminaLayer" />`. MSBuild writes it to a generated global analyzer config as `build_property.LaminaLayer = Spec`. The analyzer reads it once per compilation from `CompilationStartAnalysisContext.Options.AnalyzerConfigOptionsProvider.GlobalOptions.TryGetValue("build_property.LaminaLayer", …)` and registers nothing if the layer doesn't apply. Two traps: `build/` assets do **not** flow to transitive consumers by default (use `buildTransitive/` too), and in-repo `ProjectReference … OutputItemType="Analyzer"` imports no package props at all, so Folio needs the `CompilerVisibleProperty` item in its own `Directory.Build.props`.
2. **LAM001.** Use symbols, not referenced assemblies. An assembly check can't work: `System.Net.Http` lives in the shared framework, so every `net10.0` project references it, and `ProjectReference` is transitive, so a spec project sees driver assemblies. BannedApiAnalyzers (RS0030) is the model: it handles a namespace ban (`N:`) by walking the containing namespaces of each used symbol, from an operation action over invocations, member references, object creation, conversions, `typeof` and so on. But it is usage-based, so it misses a field, parameter or local *declared* with a banned type and never used. LAM001 needs those declarations too. Do **not** flag `using` directives: the SDK's implicit global usings include `System.Net.Http`.
3. **LAM002/LAM004.** These are cheap. At compilation start, resolve `Thread.Sleep`, `Task.Delay` and `DateTime`/`DateTimeOffset` `Now`/`UtcNow` with `GetTypeByMetadataName`. Then run one operation action on `Invocation`, `MethodReference` (method groups) and `PropertyReference`, comparing with `SymbolEqualityComparer.Default`. BannedApiAnalyzers could do the same detection with a `BannedSymbols.txt`, but only with its single ID, RS0030, and only if the consumer installs it. The coding standards package already bans `DateTime.Now`/`DateTimeOffset.Now` (**not** `UtcNow`) in this repo only. So Lamina needs its own rules; BannedApiAnalyzers covers none of LAM002/LAM004 for Lamina users.
4. **LAM003.** A symbol action on `Method`, `Property`, `Field` and `Event`, gated on `LaminaLayer=Dsl`. Report only when the member is *effectively* public (it and every containing type are public). Walk the return type, parameter types, generic type arguments (so `Task<HttpResponseMessage>` is caught), array element types and pointer/ref types. Skip `override` and explicit interface implementations so one violation gives one diagnostic, at the declaration that introduced it.
5. **Generated code.** Call `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)`. Roslyn treats a tree as generated if its file name ends `.g.cs`, `.generated.cs`, `.designer.cs` or `.g.i.cs`, starts `TemporaryGeneratedFile_`, opens with an `<auto-generated` or `<autogenerated` comment, or has `generated_code = true` in an analyzer config. Symbols with `[GeneratedCode]` are also generated. Analyzers run on the compilation *after* generators, so they do see the channel generator's output. That output is `*.g.cs` with `// <auto-generated/>`, so it is skipped twice over. It is also harmless: each generated class is an empty sealed subclass with a `[Trait]`, so a violation in the abstract spec class is reported once, in user code.
6. **Testing.** Use `CSharpAnalyzerTest<TAnalyzer, DefaultVerifier>` from Microsoft.CodeAnalysis.CSharp.Analyzer.Testing 1.1.4. `DefaultVerifier` throws `InvalidOperationException`, so it works under xUnit v3 with no adapter package. The deprecated `.XUnit` package must not be used. Set `build_property.LaminaLayer` in a test with `TestState.AnalyzerConfigFiles` (a global config). For "fails the demo build", build a deliberately broken project that isn't in `Folio.slnx`, in its own CI step, with `-p:ErrorLog=violations.sarif,version=2.1`. Assert that the build fails **and** that the SARIF contains each expected LAM rule ID, so an unrelated compile error can't pass the check.

## 1. Reading an MSBuild property in an analyzer

### The mechanism

- The Roslyn cookbook: "MSBuild will automatically translate specified properties and metadata into a global analyzer config that can be read by a generator. A generator author specifies the properties … by adding items to the `CompilerVisibleProperty` and `CompilerVisibleItemMetadata` item groups. These can be added via a props or targets file when packaging the generator as a NuGet package." The value appears as `build_property.<Name>` in `GlobalOptions` ([source-generators.cookbook.md L541-L554](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/docs/features/source-generators.cookbook.md?plain=1#L541-L554)).
- The cookbook says "generator". The file it writes is an ordinary analyzer config, though. `GenerateMSBuildEditorConfigFileCore` evaluates each `CompilerVisibleProperty`, writes the generated file, and adds it to `EditorConfigFiles` ([Microsoft.Managed.Core.targets L163-L190](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/Compilers/Core/MSBuildTask/Microsoft.Managed.Core.targets#L163-L190)). Every `DiagnosticAnalyzer` sees analyzer configs through `AnalyzerOptions.AnalyzerConfigOptionsProvider`. So analyzers read it the same way: `context.Options.AnalyzerConfigOptionsProvider.GlobalOptions.TryGetValue("build_property.LaminaLayer", out var layer)`.
- The file is only written when there is at least one `CompilerVisibleProperty` or metadata item, and `GenerateMSBuildEditorConfigFile` isn't `false` ([targets L167-L174](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/Compilers/Core/MSBuildTask/Microsoft.Managed.Core.targets#L167-L174)).
- Data loss: values pass through editorconfig syntax, so `;` (a comment character) and other non-trivial values are mangled ([cookbook L586](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/docs/features/source-generators.cookbook.md?plain=1#L586), roslyn#51692). `Spec`, `Dsl`, `Driver` are single words, so this doesn't bite. Compare values case-insensitively and treat a missing or empty value as "not a Lamina layer".
- Read it **once**, in a `RegisterCompilationStartAction`, and register the layer's actions only when they apply. A project with no `LaminaLayer` then costs one dictionary lookup.

### Shipping the props in the package

- NuGet imports `build/<package_id>.props` and `.targets` automatically; the file name must match the package ID ([MSBuild props and targets in a package](https://learn.microsoft.com/en-us/nuget/concepts/msbuild-props-and-targets)). The cookbook's full example packs the analyzer DLL to `analyzers/dotnet/cs` and the props to `build` ([cookbook L603-L628](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/docs/features/source-generators.cookbook.md?plain=1#L603-L628)). `Lamina.XunitV3.csproj` already packs its generator DLL the same way.
- **Transitive flow.** The default `PrivateAssets` is `contentfiles;analyzers;build` ([PackageReference in project files](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files)). So if `Lamina.Dsl` (say) depends on `Lamina.Analyzers` with a plain reference, the dependency is written with `exclude="Build,Analyzers"`, and a consumer of `Lamina.Dsl` gets **neither** the analyzer nor its props. Folders that do flow: `buildTransitive/` (NuGet 5.0+, "build logic for assets that flow transitively to any consuming project") ([MSBuild props and targets](https://learn.microsoft.com/en-us/nuget/concepts/msbuild-props-and-targets)). The analyzer DLL itself flows only if the referencing package sets `PrivateAssets="none"` (or omits `analyzers`) on that reference. This is a packaging decision for later: either templates reference `Lamina.Analyzers` directly in each layer project, or a layer package depends on it with `PrivateAssets="none"` and `Lamina.Analyzers` ships the props in both `build/` and `buildTransitive/`.
- **In-repo use.** Folio uses project references. `ProjectReference` with `OutputItemType="Analyzer"` loads the DLL but imports no `.props` from it. The existing `Lamina.XunitV3.csproj` comment already notes that project references don't pass analyzers on. So Folio must declare `<CompilerVisibleProperty Include="LaminaLayer" />` itself (one line in `folio/Directory.Build.props`, or an explicit `<Import>` of the analyzer's props file), and each layer project needs its own analyzer `ProjectReference`. The packaging-stage CI job (Plan §9) is what proves the props really ship.
- A package with only `analyzers/` and `build/` and no `lib/` is compatible with every framework. Pack raises NU5127 if the build files sit only in framework-specific subfolders ([MSBuild props and targets](https://learn.microsoft.com/en-us/nuget/concepts/msbuild-props-and-targets)). Put them in the root `build/` folder.

### Project setup (unchanged from the generator)

- `netstandard2.0`, `IsRoslynComponent`, `EnforceExtendedAnalyzerRules`, Microsoft.CodeAnalysis.CSharp 5.0.0 with `PrivateAssets="all"`, PolySharp: exactly as `Lamina.XunitV3.Generators.csproj`. RS1036 requires `EnforceExtendedAnalyzerRules` in any project that contains analyzers or generators ([Microsoft.CodeAnalysis.Analyzers.md](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.Analyzers/Microsoft.CodeAnalysis.Analyzers.md)).
- **New for an analyzer: release tracking.** Microsoft.CodeAnalysis.Analyzers (already present, via Microsoft.CodeAnalysis.Common) expects `AnalyzerReleases.Shipped.md` and `AnalyzerReleases.Unshipped.md` as `AdditionalFiles` in any project that declares `DiagnosticDescriptor`s, and warns (RS2008) otherwise ([ReleaseTrackingAnalyzers.Help.md](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.Analyzers/ReleaseTrackingAnalyzers.Help.md)). Under the repo's warnings-as-errors, that fails the build. The generator never hit this because it declares no descriptors.
- Nothing used here is newer than Roslyn 5.0.0: `IOperation` actions, `ConfigureGeneratedCodeAnalysis`, `AnalyzerConfigOptionsProvider` and `SymbolEqualityComparer` all predate it. ADR 0004's baseline holds for the analyzer too.

## 2. LAM001: infrastructure namespaces in spec and DSL projects

### Why not a referenced-assembly check

- `System.Net.Http` is part of `Microsoft.NETCore.App`, so it is referenced by every `net10.0` project. An assembly-level check can't tell "uses it" from "has it".
- `ProjectReference` is transitive by default, so a spec project that (directly or through a test host) reaches a driver project has Playwright, WireMock and so on in its compilation references. It would be flagged even when spec code never touches them.
- Where an assembly check *is* right: as a cheap gate. At compilation start, if none of the banned namespaces resolve in `compilation` (for example, `GetTypeByMetadataName("Microsoft.Playwright.IPage")` is null and no referenced assembly name starts `Microsoft.Playwright`), skip registering the Playwright part. `System.Net.Http` can never be gated out this way.
- And for LAM004: "a SUT project that references `Lamina.Runtime`" **is** an assembly question. `compilation.ReferencedAssemblyNames` containing `Lamina.Runtime` is the right test, with no `LaminaLayer` needed.

### How BannedApiAnalyzers does it (the model)

- Namespaces can be banned with `N:Namespace` entries ([BannedApiAnalyzers.Help.md](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/BannedApiAnalyzers.Help.md)). A type is banned if any containing namespace is ([SymbolIsBannedAnalyzerBase.cs L350-L378](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/Core/SymbolIsBannedAnalyzerBase.cs#L350-L378)).
- It registers one operation action over `ObjectCreation`, `Invocation`, `EventReference`, `FieldReference`, `MethodReference`, `PropertyReference`, `ArrayCreation`, `AddressOf`, `Conversion`, `UnaryOperator`, `BinaryOperator`, `Increment`, `Decrement`, `TypeOf`. It checks the target symbol and its containing type. It adds syntax actions for base lists and XML `cref`s, and a symbol action for attributes ([L42-L185](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/Core/SymbolIsBannedAnalyzerBase.cs#L42-L185)), from source.
- **Gap for LAM001:** nothing there fires on a *declaration*. `private IPage _page;`, a parameter `HttpClient client`, or a local `HttpResponseMessage r = await dsl.Get();` that is only passed along produces no operation that names the type's member. LAM001's intent ("references infrastructure") needs these. Add a symbol action on `Field`, `Property`, `Method` (return and parameter types), `NamedType` (base type, interfaces, type parameter constraints), and an operation action on `VariableDeclarator` for locals, all using the same "is any containing namespace banned" check. Walk generic type arguments and array element types so `List<IPage>` is caught.
- Deduplicate per syntax node: a single line like `var r = await http.GetAsync(url);` hits the invocation, the containing type and the local's type.

### False-positive risks

- **Implicit usings.** `Microsoft.NET.Sdk` adds `global using System.Net.Http;` by default ([.NET project SDK overview](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview#implicit-using-directives)). So never flag `using` directives. (The generated `GlobalUsings.g.cs` would be skipped as generated anyway, but a hand-written `global using` would not.) Flag uses only.
- **Neighbouring namespaces.** Match on the namespace *boundary*: `System.Net.Http` and its children (`System.Net.Http.Json`, `System.Net.Http.Headers`), but not the parent `System.Net`, which holds `HttpStatusCode`. Whether a DSL may expose `HttpStatusCode` is a design call; it must not be caught by accident. Compare `INamespaceSymbol` chains, not strings with `StartsWith` (which would also match an unrelated `System.Net.HttpX`).
- **Lamina's own types.** `Lamina.Dsl` and `Lamina` types that wrap HTTP internally are fine: the rule looks at the namespace of the symbol used, not at what it calls.
- **Generated code.** The channel generator emits only `global::Xunit.Trait`, so it can't trigger LAM001 even if analysed.
- **Which list.** Plan §6.9 names Playwright, `System.Net.Http`, WireMock, Confluent.Kafka, Appium. Hard-code that list in the analyzer for now. An `.editorconfig` key (e.g. `lamina_lam001.additional_namespaces`) could extend it later; analyzer config is per-tree and needs no extra MSBuild plumbing.

## 3. LAM002 and LAM004: sleeps and wall-clock reads

### Detection

- At compilation start: `compilation.GetTypeByMetadataName("System.Threading.Thread")`, `"System.Threading.Tasks.Task"`, `"System.DateTime"`, `"System.DateTimeOffset"`, then pick out the members (`Sleep`, all `Delay` overloads, `Now`, `UtcNow`). If none of the layer's rules apply, register nothing.
- One operation action for `OperationKind.Invocation` (calls), `OperationKind.MethodReference` (method groups, e.g. `Func<TimeSpan, Task> wait = Task.Delay;`) and `OperationKind.PropertyReference` (the property getters). Compare `IInvocationOperation.TargetMethod.OriginalDefinition` / `IPropertyReferenceOperation.Property` with `SymbolEqualityComparer.Default`. This is the same shape as BannedApiAnalyzers' operation action, so cost is one symbol comparison per call site.
- `Task.Delay` has `TimeProvider` overloads on .NET 8+. LAM002 as written bans all of them in spec, DSL and driver code. Whether to allow `Task.Delay(…, timeProvider)` is a design question; detecting the difference is one `Parameters` check.
- Not caught by a symbol list (and out of scope unless the design wants it): `SpinWait`, `Thread.SpinWait`, `new Timer(...)`, `TimeProvider.System.GetUtcNow()`, `Stopwatch`, `Environment.TickCount`.
- LAM004's gate is assembly-based (see LAM001), not `LaminaLayer`: SUT projects are not test layers.

### Does an existing analyzer already cover it?

- **BannedApiAnalyzers** can express all of LAM002 and LAM004 as `BannedSymbols.txt` entries (`M:System.Threading.Thread.Sleep(System.Int32)`, `P:System.DateTime.UtcNow`, …) ([help](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/BannedApiAnalyzers.Help.md)). But: every hit is RS0030, not LAM002/LAM004, so severity and suppression can't be per rule. It only runs if the consumer has installed the package. And it can't be gated on `LaminaLayer` or on referencing `Lamina.Runtime`. Shipping a `BannedSymbols.Lamina.txt` as `AdditionalFiles` through a props file would quietly ban the APIs in *every* project of a consumer who happens to use BannedApiAnalyzers. So it is a design reference, not a delivery mechanism.
- **Opinionated.DotNet.CodingStandards 0.0.22** (this repo only, never shipped). Its `BannedSymbols.NonUtcDates.txt` bans `P:System.DateTime.Now` and `P:System.DateTimeOffset.Now` with "Use … UtcNow instead", plus the local-time `File`/`Directory`/`FileSystemInfo` members. It does **not** ban `UtcNow`, and it has nothing on `Thread.Sleep`/`Task.Delay`. Its RS0030 severity is `warning` (an error here only through warnings-as-errors). So in Folio, `DateTime.Now` already fails the build; `DateTime.UtcNow` doesn't. Plan §9.1's line "its ban on UTC date APIs pushes Folio's services towards `TimeProvider`" is inaccurate: the ban pushes code *to* `UtcNow`. LAM004 is what pushes towards `TimeProvider`.
- BannedApiAnalyzers analyses generated code by default (opt out with `dotnet_banned_api_analyzer.exclude_generated_code = true`) ([help](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/BannedApiAnalyzers.Help.md); [SymbolIsBannedAnalyzerBase.cs L24, L47](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/RoslynAnalyzers/Microsoft.CodeAnalysis.BannedApiAnalyzers/Core/SymbolIsBannedAnalyzerBase.cs#L24)). That matches Plan §9.1's note that banned-API rules still apply to generator output.

## 4. LAM003: public DSL members exposing driver-level types

- `RegisterSymbolAction(…, SymbolKind.Method, SymbolKind.Property, SymbolKind.Field, SymbolKind.Event)`, gated on `LaminaLayer=Dsl`.
- **Effective accessibility.** `DeclaredAccessibility == Public` on the member *and* every `ContainingType`. A public method on an internal class is not API. Decide whether `protected` counts (it is visible to subclasses in other assemblies).
- **Types to inspect.** Return type, parameter types, property and field type, event delegate type. Recurse into `INamedTypeSymbol.TypeArguments` (so `Task<HttpResponseMessage>`, `IReadOnlyList<IPage>`, `Func<IPage, Task>` are caught), `IArrayTypeSymbol.ElementType` and `IPointerTypeSymbol`. `ref`/`out` parameters have the same `Type`.
- **Avoid duplicates.** Skip `IsOverride` members and members with `ExplicitInterfaceImplementations`; also skip implicit implementations of an interface method that is itself in a DSL project (it was reported there). Skip property accessor methods (`MethodKind.PropertyGet`/`PropertySet`) because the property symbol is reported instead.
- **What is "driver-level".** The same namespace list as LAM001, plus types from `Lamina.Drivers.*`. Reuse the LAM001 matcher.
- Location: report on the type syntax in the declaration where possible (`IMethodSymbol.DeclaringSyntaxReferences` → `MethodDeclarationSyntax.ReturnType`), else the identifier.

## 5. Generated code and the channel generator

- **Opt out.** `context.ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` means no callbacks and no diagnostics in generated code. RS1025/RS1026 (Microsoft.CodeAnalysis.Analyzers) flag an analyzer that doesn't call `ConfigureGeneratedCodeAnalysis` and `EnableConcurrentExecution`.
- **What Roslyn calls generated** ([GeneratedCodeUtilities.cs](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/src/Compilers/Core/Portable/SourceGeneration/GeneratedCodeUtilities.cs), from source):
  - a file name starting `TemporaryGeneratedFile_`, or ending `.designer`, `.generated`, `.g` or `.g.i` before the extension (L61-L78);
  - a leading comment containing `<autogenerated` or `<auto-generated` (L16);
  - `generated_code = true` (or `false`, to override) in an analyzer config (L152-L166);
  - a symbol (or containing symbol) with `System.CodeDom.Compiler.GeneratedCodeAttribute` (L18-L45).
- **Do analyzers see generator output?** Yes. The source generators design: "generator diagnostics only on the first compilation, analyzer diagnostics only on the second compilation" ([source-generators.md](https://gh.ali360.cloudns.ch/dotnet/roslyn/blob/20b549bac1409a0df9f4575557c71f6a7e506989/docs/features/source-generators.md?plain=1)). The second compilation includes the generated trees.
- **The channel generator's output** is named `<Namespace>.<Class>_<Channel>.g.cs` and starts `// <auto-generated/>` (`ChannelGenerator.cs`), so it matches two rules above. It contains a sealed subclass with a `[global::Xunit.Trait]` and no members. Spec bodies stay in the user's abstract class, so LAM001/LAM002 report once there, not once per channel. If a future generator copied user code into its output, those violations would be silently hidden; keep generated classes free of user code.
- **Testing support.** `Microsoft.CodeAnalysis.Testing` re-runs every test with ` // <auto-generated>` prepended to each source and expects the diagnostics to disappear, unless the analyzer opts into generated code or the test sets `TestBehaviors.SkipGeneratedCodeCheck` ([AnalyzerTest`1.cs L456-L479](https://gh.ali360.cloudns.ch/dotnet/roslyn-sdk/blob/affadd0b5aa3f4c30f97d317497f63c6ffdc94b0/src/Microsoft.CodeAnalysis.Testing/Microsoft.CodeAnalysis.Analyzer.Testing/AnalyzerTest%601.cs#L456-L479)). It does the same with `#pragma warning disable`. So the generated-code opt-out is tested for free.

## 6. Testing

### Microsoft.CodeAnalysis.Testing with xUnit v3

- Use `Microsoft.CodeAnalysis.CSharp.Analyzer.Testing` 1.1.4 and `CSharpAnalyzerTest<TAnalyzer, DefaultVerifier>`. `DefaultVerifier` reports failures by throwing `InvalidOperationException` with a message ([DefaultVerifier.cs L20-L88](https://gh.ali360.cloudns.ch/dotnet/roslyn-sdk/blob/affadd0b5aa3f4c30f97d317497f63c6ffdc94b0/src/Microsoft.CodeAnalysis.Testing/Microsoft.CodeAnalysis.Analyzer.Testing/DefaultVerifier.cs#L20-L88)), so any test framework, xUnit v3 included, sees a failed test. The xUnit-specific package is deprecated and built for xUnit v2; don't use it.
- **Roslyn version.** The testing package depends on `Microsoft.CodeAnalysis.CSharp.Workspaces` **≥ 1.0.1**. Without an explicit reference, NuGet picks 1.0.1. Add `Microsoft.CodeAnalysis.CSharp.Workspaces` 5.0.0 to `Directory.Packages.props` and reference it from `Lamina.Analyzers.Tests`, so tests run the same Roslyn as the analyzer. The `outdated` check already excludes the `Microsoft.CodeAnalysis.` prefix (ADR 0004), and the `.Analyzer.Testing` packages fall under that prefix too, so they won't be flagged either: bump them by hand.

### Proving "fails the demo build" in CI

Facts that shape it:

- An analyzer error fails `dotnet build` with a non-zero exit code. LAM003/LAM004 are warnings; they fail only under warnings-as-errors (on in this repo through the coding standards).
- `-p:ErrorLog=<file>,version=2.1` makes the compiler write every compiler and analyzer diagnostic to a SARIF 2.1.0 file ([Errors and warnings compiler options](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/errors-warnings#errorlog)). The default version is "1", so pass `version=2.1`.
- A project that is **not** in `Folio.slnx` isn't built by the normal `build` job, so its deliberate errors don't break CI.

So: a `folio/tests/Violations/…` project per layer (or one with each layer's file set via `<LaminaLayer>` per project), each holding one violation per rule and nothing else wrong. A CI step builds them with `ErrorLog`, expects a non-zero exit, then checks the SARIF `results[].ruleId` set equals exactly `{LAM001, LAM002, LAM003, LAM004}`. Checking IDs, not just the exit code, stops a typo or a missing reference from passing as "the analyzer worked". The same step proves the in-repo wiring (analyzer `ProjectReference` plus `CompilerVisibleProperty`). Once the packaging stage exists (Plan §9, from a later phase), running it against the packed `.nupkg` also proves the shipped `build/` props.

## Surprises that affect later decisions

1. **Package props don't reach transitive consumers** by default, and analyzers don't either. How `Lamina.Analyzers` reaches user projects (direct reference from templates, or `PrivateAssets="none"` from a layer package plus `buildTransitive/`) must be decided.
2. **In-repo, the props are never imported.** Folio needs its own `CompilerVisibleProperty` line; without it every rule silently does nothing, and the analyzer unit tests would still pass. The violations project in CI is what catches this.
3. **Release tracking (RS2008)** will fail the first analyzer build under warnings-as-errors until `AnalyzerReleases.*.md` exist.
4. **The test package defaults to Roslyn 1.0.1 and to net8.0 reference assemblies**, and downloads reference packs at test time. Pin Workspaces 5.0.0 and pick `Net100` explicitly.
5. **Plan §9.1 is wrong about the coding standards' date ban.** It bans `DateTime.Now`, not `UtcNow`. LAM004 has no overlap with it beyond `Now`.
6. **Implicit usings add `System.Net.Http` to every project**, so LAM001 must flag uses, never `using` directives.
